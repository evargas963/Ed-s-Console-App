What the chip is supposed to do

Whenever price is hovering near a nearest key level (Gamma Wall, OI wall, Pin, Charm Drift, etc., whichever is closest to spot), this chip counts how many times that level has been tested in the last 6.5 hours — backed by db.count_level_tests() reading level_crosses.

  • 1st–2nd test: random touches — quiet, dim chip
  • 3rd test: "building" — amber chip, the level is starting to matter
  • 4th+ test (current screenshot): "hot" — red chip; institutional flow is repeatedly probing the level → expect either a break (acceleration trade) or a strong reversal (level holds, fade trade)

Current rendering is just "4TH TEST OF PUT G-WALL" in a tiny red pill. It surfaces the count but hides the price, distance, direction breakdown, and pattern interpretation.

Design notes
  1. Severity ramp: dim / amber / red — same color contract as Entry armed / Stack degraded in the signal-rail-card. Operator learns one severity vocabulary.
  2. Direction split: 1↑ rejected vs 2↓ held tells the operator the level is acting as support (rejections from below) or resistance (rejections from above) — institutionally meaningful, currently hidden.
  3. Pattern copy (Option B only): the "break-through vs strong hold" line is the institutional-bar payoff. Without it the operator has to know what 4 touches of a Put Gamma Wall typically resolves to.
  4. Where it lives: Option A — stays in the existing chip ribbon (lowest risk, no new chrome). Option B — appears as a row-level surface below the signal-rail-card when ≥3 prior tests; collapses back to a compact chip at ≤2. Option C — sits as a thin strip; less verbose than B, more visible than A.
  5. No wire change required: all data already comes from /api/level_crosses + db.count_level_tests() + nearest_above/nearest_below fields on the payload. Just present it.

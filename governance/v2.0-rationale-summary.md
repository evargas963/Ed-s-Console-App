# Framework v2.0 — rationale summary

**Status:** DRAFT rationale companion  
**Target draft:** `governance/Framework-ED-Decision-Engine-v2.0-DRAFT.md`  
**Target lock:** `governance/FRAMEWORK_V2_TARGET_LOCK_RECORD.md`

Purpose: durable summary of the architecture decisions that shaped the v2.0 target. This file records why the framework is structured as a meta-framework and why Pilot 1 / Pilot 1B are sequenced the way they are.

---

## Meta-Framework, Not One Horizon Stack

**Decision:** v2.0 is a meta-framework for strategy modules, not one model stretched from 1m to LEAPS.

**Rationale:** Short-horizon trading, swing trading, long-horizon equity/LEAPS, 0DTE options, and on-demand portfolio analysis have different signal sources, label families, validation methods, lifecycle actions, expression choices, and operating rhythms. Treating them as one continuous horizon axis would force incompatible evidence standards into one contract.

**Resulting structure:**
- Module A: short-horizon event-driven trading.
- Module B: swing trading.
- Module C: long-horizon equity / LEAPS.
- Module D: on-demand portfolio analysis.

---

## Four Edge Domains

**Decision:** All modules are audited across Signal, Implementation, Portfolio, and Lifecycle Edge.

**Rationale:** Entry prediction alone is not enough. Realized edge depends on whether the opportunity can be expressed, whether it fits the current book, and how the open position is managed. Lifecycle Edge was separated because exit timing, scale-out, thesis-break, timeout-extension, and conversion actions have their own evidence requirements and failure modes.

---

## Strategy Module vs Expression Profile

**Decision:** Separate strategy modules from expression profiles.

**Rationale:** The module answers why/when to seek exposure. The expression profile answers how that exposure is expressed. This keeps a short-horizon bullish SPY signal distinct from the choice to express it as shares, a call, a vertical spread, or a 0DTE structure.

**Key taxonomy:**
- Strategy Module = why/when.
- Expression Profile = how.
- Portfolio Layer = whether allowed alongside the book.
- Lifecycle Policy = how managed after entry.

---

## 0DTE Preservation As A2

**Decision:** 0DTE remains explicitly in scope as Module A, Expression Profile A2.

**Rationale:** The original project vision included a 0DTE model. The v2 restructuring preserves that goal while avoiding the mistake of treating 0DTE as just another equity horizon. A2 shares Module A's short-horizon signal logic where appropriate, but it requires separate option-chain, **`volatility`**, Greeks, execution, lifecycle, payoff-label, and validation contracts.

**Pilot sequence impact:**
- Pilot 1: Module A / A1 equity-ETF on SPY.
- Pilot 1B: Module A / A2 options-0DTE on SPY / QQQ unless amended.

---

## Pilot 1 Before Pilot 1B

**Decision:** Build Module A/A1 first, then add A2.

**Rationale:** The current app already has a strong A1 spine: 1m snapshots, horizon labels, ML stack, Tier C payload, and UI prediction/fusion surface. A2 currently exists mostly as downstream option-expression scoring and replay. Validating the underlying signal path first reduces the risk of debugging signal and options-expression failures at the same time.

---

## Tier C First

**Decision:** v2 decision-complete outputs live on Tier C first.

**Rationale:** The current L1/Tier B contract is intentionally light and excludes chain, DB, ML, and full `build_market_state`. Pushing v2 decisions into Tier B would violate the existing plane contract. Tier B may later show cached decision headlines, but fresh v2 decision authority belongs to Tier C unless the plane contract is explicitly amended.

---

## Event Reconciliation

**Decision:** Event reconciliation is a required layer before candidate decisions.

**Rationale:** Multi-source detectors can fire on the same underlying catalyst. Without clustering and contradiction handling, the system can double-count the same signal or emit conflicting candidates. One reconciled candidate per ticker/time/catalyst cluster is the default unless preregistered otherwise.

---

## Cross-Module Coordination

**Decision:** Portfolio Edge coordinates across modules and includes conflict handling.

**Rationale:** The same ticker can be held by Module C, evaluated by Module B, and traded intraday by Module A. Without cross-module coordination, individually valid module outputs can become globally contradictory.

**Default outcomes:**
- approved hedge;
- thesis-break escalation;
- blocked lower-priority trade;
- no conflict.

---

## Hedge Contracts

**Decision:** Hedges require pre-registered hedge contracts.

**Rationale:** "It is a hedge" cannot be a runtime discretionary override. Hedge exceptions must be governed so they do not swallow the long-horizon veto or bypass risk controls.

Required fields:
- `hedge_contract_id`;
- `protected_module`;
- `hedging_module`;
- ticker / exposure scope;
- allowed side;
- max hedge size;
- max duration;
- trigger conditions;
- attribution target;
- expiry / review cadence.

---

## Module D As Meta-Consumer

**Decision:** Module D consumes all modules rather than wrapping only long-horizon Module C.

**Rationale:** A user question such as "Should I buy AAPL?" may need short-horizon timing context, swing context, long-horizon thesis context, tax/account constraints, and portfolio exposure. Module D is a recommendation and explanation surface, not an autonomous trading module.

Required outputs include recommendation, rationale, module contributions, confidence/disagreement, constraints, user-horizon alignment, and what would change the answer.

---

## Per-Module Validation

**Decision:** Validation contracts are module-specific.

**Rationale:** Minute-bar strategies have many samples and require purged walk-forward discipline; swing trades have fewer samples and need factor attribution; long-horizon/LEAPS strategies need cross-sectional pooling and multi-year holdouts; 0DTE needs option-chain and payoff validation. One validation standard cannot honestly cover all modules.

---

## Approximate Guarantees

**Decision:** v2.0 includes an approximate-guarantee concept.

**Rationale:** Methods such as conformal prediction, DSR, bootstrap intervals, and CV estimates depend on assumptions that market data can violate. Reports must name the assumption, likely violation, any assumption-relaxed variant, and empirical diagnostics showing whether the approximation held.

---

## Post-Trade Attribution

**Decision:** v2.0 requires a post-trade attribution loop.

**Rationale:** The system must learn from closed trades, not only from static backtests. Close-out records should decompose realized P&L into signal, execution, portfolio, lifecycle, and tax contributions where applicable, then feed calibration, execution, lifecycle, and refit cycles.

---

## Tax Overlay

**Decision:** Tax overlay is included as a decision-policy element, but implementation can be module/account dependent.

**Rationale:** For taxable individual accounts, after-tax EV may differ materially from pre-tax EV. Tax logic should not contaminate signal probability; it should adjust decision policy, lifecycle, and Module D recommendations where data is available.
